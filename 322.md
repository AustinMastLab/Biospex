# Issue #332: Queue Expedition Subject Saves

## Goal

Keep expedition create and update requests responsive by moving only the
potentially large MongoDB subject-assignment work to a dedicated
`expedition-save` Beanstalkd tube. The relational expedition record and its
editable metadata must still save synchronously so the controller can redirect
to its show page. The submitting user must receive a completion or terminal
failure email.

## Important design decisions

1. Use one `ExpeditionSaveJob`, not separate store and update jobs. The
   subject-assignment algorithm is the same for both operations; the durable
   request records whether the final save originated from a create or update
   for message and actor-contact behavior.
2. Do not put `subject-ids` on the job. The form permits up to 20,000 selected
   subjects (`config.expedition_size`), and the comma-delimited list can exceed
   Beanstalkd's 64 KiB job-body limit. Persist the normalized subject IDs in
   MySQL and dispatch the job with only an expedition/request identifier.
3. Make subject synchronization retry-safe rather than trying to include
   MongoDB writes in the existing MySQL transaction. The request snapshot is
   retained until the MongoDB work and success notification enqueue succeed,
   then deleted; attach/detach operations are idempotent.
4. Coalesce rapid submissions for the same expedition. A revision number and a
   unique job lock prevent concurrent subject mutation. If the request changes
   while a job is running, it re-runs against the latest persisted snapshot and
   sends the completion notification only for that latest revision.
5. Keep the success/failure email on the existing queued `Generic`
   notification path (`default` tube). The long-running MongoDB work alone
   belongs on `expedition-save`.

## Implementation plan

1. **Finish the queue and deployment configuration.**
   - Retain the existing `config('config.queue.expedition_save') =>
     'expedition-save'` entry in `config/config.php`.
   - Add `QUEUE_EXPEDITION_SAVE` to `config.deployment_fields`. The
     `app:deploy-files` command only replaces Supervisor placeholders named in
     that allow-list; without this, the deployed worker would literally listen
     to `QUEUE_EXPEDITION_SAVE`.
   - Keep the `QUEUE_EXPEDITION_SAVE` program in
     `resources/supervisor/queues.conf`, with the long-work profile used by
     export jobs (`--timeout=7500`, `--max-time=21600`, and
     `stopwaitsecs=3600`).
   - Keep `numprocs=1` because subject mutations against one expedition must
     remain serialized. The job lock provides correctness if this is increased
     later, but one worker avoids competing large MongoDB writes across
     expeditions until production capacity is measured.
   - Keep the program in `resources/supervisor/group.conf`, remove the
     accidental space before its name, and preserve the file's one-line
     placeholder format.

2. **Persist pending subject-save work in MySQL.**
   - Create an `expedition_save_requests` migration, model, factory, and
     expedition relationship. Give it a unique `expedition_id`, the submitting
     `user_id`, operation (`create` or `update`), normalized `subject_ids`
     JSON, monotonically increasing `revision`, status, and timestamps.
   - Store only unique, non-empty IDs. Retaining this snapshot lets jobs retry
     after a worker restart and ensures the controller never serializes a large
     form field into Beanstalkd.
   - Upsert the one request row for each expedition inside the same MySQL
     transaction that creates or updates the expedition metadata. Increment
     `revision` on every submission.
   - Dispatch the job only after the transaction commits. If the relational
     save rolls back, neither a request record nor a job may survive. Keep
     failed requests for retry and diagnosis, but delete successful requests
     so selected subject IDs do not accumulate in MySQL.

3. **Split `ExpeditionService` into synchronous metadata persistence and
   asynchronous subject synchronization.**
   - Change `store()` and `update()` to retain their existing logo handling,
     workflow/completed-state rules, validation boundary, and authorization
     checks, but remove direct `setSubjectIds()`, MongoDB attachment/detachment,
     stats, actor synchronization, and MongoDB rollback from their MySQL
     transactions.
   - Have the service create/update the durable save request and return the
     saved expedition; the controller will dispatch the job after commit.
   - Move subject synchronization into focused service methods used by the job.
     Load the request snapshot, find the current subject IDs, calculate attach
     and detach differences, then update the expedition stat and actor totals
     only after MongoDB subject updates finish.
   - Replace the current per-subject `find()`/`save()` loops with chunked
     MongoDB bulk updates (`$addToSet` with `$each` and `$pull` with `$in`).
     Chunking bounds BSON command size and memory while eliminating thousands
     of individual round trips. Count the successfully assigned MongoDB
     subjects for `local_subject_count` and actor totals instead of trusting the
     submitted ID count.
   - Preserve the existing rule that subject changes are skipped when a
     workflow manager exists. The job must still notify the user with an
     accurate no-subject-change completion message and clean up the successful
     request row.

4. **Create `App\Jobs\ExpeditionSaveJob`.**
   - Dispatch it to `config('config.queue.expedition_save')`, pass only the
     expedition/request key, set a timeout compatible with the Supervisor
     process, and use an expedition-scoped unique/overlap lock.
   - At execution, retrieve the latest request snapshot and its revision,
     mark it processing, run the bulk subject synchronization, then re-read
     the request. If a newer revision arrived, release/re-run the same job
     instead of emailing a stale completion.
   - On the stable latest revision, run the existing actor synchronization and
     new-expedition actor-contact notification only when the operation is
     `create`, enqueue the submitting user's `Generic` completion
     notification, then delete the successful request row and its selected
     subject IDs from MySQL.
   - Implement `failed(Throwable)` to mark the request failed and send the
     submitting user a failure email copied to the configured administrator,
     following the existing long-running job convention. Include actionable
     expedition context but do not expose a stack trace to non-admin users.
   - Ensure retry behavior remains idempotent: rerunning an already-applied
     snapshot must not duplicate expedition IDs in a subject or duplicate
     actor/stat records.

5. **Update `ExpeditionController` and user-facing messages.**
   - In `store()` and `update()`, continue loading the same project/group
     relationships and applying `CheckPermission`; pass only
     `$request->validated()` data to the service.
   - Dispatch `ExpeditionSaveJob` after the synchronous metadata/request save.
     Redirect to the newly created or updated expedition as today.
   - Replace the two expedition success flash messages consumed by
     `bootstrap-notify` with operation-specific wording that the subject-add
     job was submitted and that email will confirm completion. Do not change
     the generic create/update messages used by unrelated controllers.
   - Keep synchronous validation, authorization, and relational-save failures
     on their current danger redirect paths; a job failure is reported later by
     email rather than appearing as a false success.

6. **Add Pest coverage as each layer is implemented.**
   - Add `tests/Feature/Admin/ExpeditionControllerTest.php` using the existing
     admin-controller test conventions. For authorized store and update
     requests, fake the queue; assert the redirect and new submitted-job flash
     text, the expedition metadata, the durable request snapshot/revision, and
     an `ExpeditionSaveJob` pushed to the `expedition-save` tube.
   - Cover validation and unauthorized create/update paths: they must not
     create a save request or dispatch a job.
   - Add job/service tests for an initial create selection, update
     attach/detach differences, workflow-manager no-op behavior, idempotent
     retry, superseding revision behavior, completion notification, successful
     request cleanup, and terminal-failure request retention/notification. Use
     Laravel queue/notification fakes and mock only the MongoDB boundary; do
     not require a live MongoDB instance for controller tests.
   - Exercise bulk-operation chunk boundaries with a dataset, including an
     empty selection and a selection exceeding one chunk. Assert that the
     observed stat/actor count reflects assigned subjects.
   - Run the narrow Expedition controller/job tests after each change, then
     `vendor/bin/pint --dirty --format agent`.

## Cross-system verification

- **Web request -> MySQL:** create/edit an expedition with selected subjects;
  confirm immediate metadata persistence, a single pending save request, and
  the submitted-job flash notice.
- **MySQL -> Beanstalkd -> MongoDB:** verify the worker consumes
  `expedition-save`, applies the expected attach/detach changes in chunks,
  updates stats/actors, queues the completion email, and deletes the
  successful MySQL request row.
- **MongoDB -> email:** confirm the submitting user receives one completion
  email; force a terminal failure and confirm the user plus administrator
  receive the failure notification.

## Items intentionally not included

- No change to unrelated controllers' “Record was created/updated
  successfully” notifications.
- No new Beanstalkd connection: this is a named tube on the existing
  `beanstalkd` connection.
- No separate create/update job classes: one durable, revision-aware job avoids
  duplicated logic and stale concurrent subject assignments.
